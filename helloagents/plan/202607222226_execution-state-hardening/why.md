# 变更提案: 任务执行状态机加固与质量门

## 需求背景

项目已具备“需求理解 -> 候选计划 -> 用户确认 -> 执行 -> 证据化报告”的完整链路，且报告 V2 已能区分事实证据与模型推断。当前的主要风险不在分析能力本身，而在执行生命周期的边界：同一任务可以被重复执行，媒体预检失败可能在任务已进入 `executing` 后发生，API 也无法向前端区分用户可修复错误与外部依赖失败。

这会造成重复工具调用、额外模型成本、审计记录被覆盖，以及前端展示长期“执行中”的错误状态。现有单元测试、注册表 lint 和 Web 构建可通过，但尚未覆盖真实 HTTP 路由上的状态冲突与错误码语义，也没有 CI 强制执行这些质量门。

## 变更内容

1. 将任务执行入口收敛为数据库条件更新的原子状态迁移，保证一项任务在同一时刻只能被一个执行请求领取。
2. 将媒体与计划前置条件校验移到领取执行状态之前；校验失败不得改变任务状态。
3. 建立领域错误到 HTTP 状态码的稳定映射，区分 `422` 前置条件、`409` 状态冲突和 `502/504` 外部执行失败。
4. 将 Express 应用构建与端口监听分离，使用原生 Node HTTP 测试真实路由、认证、状态码和重复请求行为。
5. 将 TypeScript、单元测试、注册表/知识库 lint 与 Web 构建收敛为 CI 质量门。
6. 为报告反馈补充只读聚合与离线评测入口，使评分、采纳率和证据质量可用于后续回归，而不直接驱动模型训练或自动调度。

## 影响范围

- **模块:** `agent-api`、`orchestrator-runtime`、`database`、`tests`、GitHub Actions、报告评测脚本。
- **文件:** `apps/agent-api/src/server.ts`、`apps/agent-api/src/routes/tasks.ts`、`apps/orchestrator-runtime/src/orchestrator.ts`、`database/repository.ts`、相关测试与工作流文件。
- **API:** `POST /api/tasks/:id/execute`、流式执行端点与恢复端点将获得确定的状态冲突和错误响应。
- **数据:** P0 不引入新业务表。以 `research_tasks.status`、`approval_state` 和已有 `updated_at` 完成原子领取；未来若改为异步多 worker，再单独评估执行租约表。

## 范围边界

- **范围内:** 同一部署数据库下的任务互斥、错误语义、HTTP 回归测试、CI、反馈评测基础。
- **范围外:** 重写报告 V2、重构所有编排模块、接入消息队列、改动外部实验室实现、自动使用用户反馈训练模型。

## 核心场景

### 需求: 原子领取任务执行
**模块:** 任务执行与持久化

用户确认计划后，首次执行请求可将任务从 `planned/awaiting_confirmation` 原子迁移为 `executing/confirmed`。后续重复点击或网络重试不得再次调用工具、Skill 或模型。

#### 场景: 两个执行请求并发到达
- 两个请求同时针对同一任务调用执行接口。
- 仅一个请求领取成功并启动步骤执行。
- 另一个请求收到 `409 TASK_ALREADY_RUNNING`，不写入执行日志、不调用外部能力。

### 需求: 前置条件失败不污染状态
**模块:** 任务执行与媒体资产

当计划要求图片而请求未携带合格媒体时，系统应明确提示用户补充输入，并保持任务等待确认状态。

#### 场景: 缺少必传设计稿
- 执行前验证所选计划的图片角色、数量和 MIME 类型。
- 返回 `422 MISSING_REQUIRED_MEDIA` 及可显示的字段信息。
- 任务仍为 `planned/awaiting_confirmation`，用户上传后可直接重试。

### 需求: 可操作的 API 失败语义
**模块:** Agent API

客户端需要区分可补充输入、重复提交、任务不存在和外部工具不可用，避免盲目重试。

#### 场景: 外部工具超时
- 已成功领取任务的工具调用超时。
- 编排器按既有容错机制将任务置为 `paused` 并保留失败记录。
- 路由返回当前执行结果或受控的外部失败状态，不把用户输入错误伪装为网关故障。

### 需求: 可回归的报告质量
**模块:** 反馈与报告回放

用户评分与历史报告回放必须能够按固定指标发现报告质量退化，但不在 P1 自动改变线上提示词或路由。

#### 场景: 新报告版本降低证据覆盖
- 使用历史任务运行 `report:replay` 生成可比较的 V2 报告。
- 比较证据引用率、无依据推断数量、行动项验证字段和人工采纳率。
- 指标未达到基线时阻止合并或标记为人工复核，而不是静默发布。

## 风险评估

- **风险:** 条件更新的允许状态定义错误，可能阻止合法恢复或放开已完成任务重跑。  
  **缓解:** 将允许迁移集中为显式状态表，覆盖开始、暂停恢复、完成后重试三类测试。
- **风险:** 先校验后领取仍可能在并发下重复通过校验。  
  **缓解:** 校验只负责输入正确性；是否允许真正执行必须由数据库条件更新决定。
- **风险:** 修改错误码影响现有前端提示。  
  **缓解:** 前端错误对象统一读取 `code` 与 `message`，保留已有错误文本作为兼容字段，并补 HTTP 集成测试。
- **风险:** CI 依赖外部模型或实验室服务导致不稳定。  
  **缓解:** CI 只运行确定性单元、fixture 与构建验证；真实网关验证保留为显式手工 smoke。
