# 正文（结论先行，给产品/设计/运营看）

## 零、分析范围与过滤（**做了范围过滤才写**；全量则省略）

一句话交代分析透镜是什么、纳入/剔除口径，让读者信任后面的分母。

```
## 分析范围与过滤
「[目标透镜，如 活动首页]」= [一句话定义它是什么]。据此先过滤、再分析：
| | 条数 | 占比 | 说明 |
|---|---|---|---|
| 纳入·[透镜]相关 | [n_in] | [x%] | [什么算相关] |
| 剔除·[原因A] | [n1] | [x%] | [如 独立程序页，各有独立入口] |
| 剔除·[原因B] | [n2] | [x%] | [如 非目标模块] |
> 下文所有频次/占比的分母 = 纳入 [n_in] 条 / 其中负面 [neg] 条。剔除项仍留在 coding-detail.csv（标"是否相关+剔除原因"），边界可复核。
```

## 一、关键问题摘要（TL;DR）

开篇就给"第一眼要看的几个具体问题"，产品/设计/运营 10 秒扫完。

```
## 关键问题摘要
**一句话主线**：[把主要问题链路一句话讲清，如"被自动报名→想退退不掉→赔钱→客服未解"]。
**最关键变量 = [X]**：[为什么它最关键，一两句 + 关键占比]。

| # | 商家/用户到底在抱怨什么 | 规模 | 不满率 | 主责 | 机会点（一句话） |
|---|---|---|---|---|---|
| 1 | [具体问题，说人话] | [n]（占不满 [x%]） | [x%] | 产品·设计·运营 | [可落地的一句话方向] |
| 2 | … | … | … | … | … |
```

> 提醒：高声量小众诉求 ≠ 多数人核心痛点；用占比与影响面校准，别被极端情绪带偏（见 VOC「局限与误用」）。

## 二、Top 痛点清单（高频 × 高负面排序）

每条 = 现象 + 规模 + 真实脱敏原话 + **产品/设计/运营三方职责** + **机会点**。

```
### 痛点 N ｜ [痛点一句话]
**规模**：[n]（占负面 [x%]），不满率 [x%]。｜**严重度**：[阻断/影响体验/轻微]
- **代表原话（脱敏）**：「[原话1]」「[原话2]」「[原话3]」
- **产品**：[功能能力/逻辑/流程/权限 层面该谁补什么]
- **设计**：[信息架构/入口可发现性/操作路径/状态反馈/事前告知/文案 层面——设计视角最易漏，务必写]
- **运营**：[规则/审核时效/活动力度/客服解决率与告知 层面]
- **机会点**：[针对这个问题能做什么，一句话可落地方向；交互/落地类标"待原型/灰度验证"]
```

> **三方别笼统写成一个"责任团队"**：同一问题往往产品/设计/运营都有份。**设计视角最易被漏**——"找不到入口""退了没反馈""静默失败没提示""客服复制粘贴话术"都是设计问题。

## 三、主题表（按 VOC 洞察输出模板逐主题）

逐主题一行。**列以运行时读到的 VOC「洞察输出模板」为准**；把模板的"责任团队"列**拆成产品/设计/运营**，并**加「机会点」列**。

```
## 主题表（频次/占比为简单计数，非统计检验；分母：[占纳入 N=… / 占负面 N=…]）

| 主题 | 频次 | 占负面% | 趋势 | 情感分 | 主责（产/设/运） | 机会点 |
|---|---|---|---|---|---|---|
| [主题名] | [n] | [x%] | [↑/↓/—，无元数据则「待补充」] | [正/负/分值] | [产品·设计·运营] | [一句话方向] |
| … | … | … | … | … | … | … |
```

> 「趋势」**只有拿到时间/版本元数据才填**，否则写「无元数据/待补充」，不要编。频次/占比要标清分母。代表原话已在 Top 痛点给过、此处可不重复（省宽度）。

## 四、关键变量 / 下钻分析（**范围内有可切分维度时才做**）

回答"哪个变量最集中地聚集了不满"。

```
## 关键变量分析
- [主轴维度] × [活动/来源类型] 矩阵（频次[负向率%]），点出最痛单元。
- 解释力：[哪个变量单独解释了多少% 的不满]。
- 次要维度（如用户分群/等级/品类）：不满率区间 [x–y%]，[有无强区分]——作方向性观察，**计数非显著性检验**（要显著性 → survey-crosstab-analysis）。
```

# 附录（方法论后置，给要追溯的人看）

## 附录 A、编码标签库（codebook）

一份带**定义 + 正反例**的多维标签体系。维度与取值**取自运行时读到的 VOC 标签体系模板**（典型为 一级模块 / 问题类型 / 情感 / 严重度 / 来源渠道），按本批数据增删。**放附录**——这是编码口径、供审稿追溯，别铺在正文开头。

> 若为**京东 App / 产品反馈**（C 端），`模块` / `问题类型` / `优先级` 维度改取自 `voc-product-line-classification.md` 的封闭词库与口径（运行时读，见 SKILL 第 2 / 3 步）；**商家侧 / 非 C 端产品线场景用通用维度**，别硬套 C 端产品线词库。

```
## 编码标签库（基于 VOC 标签体系模板，模板 status: [draft/...]）

### 维度与取值
- 一级模块 / 活动类型：[本批数据实际出现的，如 下单/支付/物流… 或 行业活动/官方活动/店铺工具…]
- 问题类型：[功能缺陷 / 易用性 / 性能 / 规则不清 / 系统异常 … 以 VOC 模板为准]
- 情感：[正向 / 负向 / 中性]
- 严重度：[阻断 / 影响体验 / 轻微]（有需要才用）
- 来源渠道：[评价 / 工单 / 开放题 / 会话 …]
- 跨切标签（可重叠，归纳出来的）：[如 被动报名/找不到入口/客服未解 …]

### 标签定义表（每个会用到的标签给定义 + 正反例，保证口径一致）
| 标签 | 定义（什么算这一类） | 正例（原话） | 反例（别误归） |
|---|---|---|---|
| [模块·问题类型] | [一句话判定标准] | 「[真实原话]」 | 「[易混但不属于的原话]」 |
| … | … | … | … |
```

> 编码本是多人/多批打标口径一致的前提：先立、再打标，不要边打边改义。新长出来的归纳主题也要补进这张表并给定义。

## 附录 B、逐条编码明细（按数据规模 N 分流）

- **N < 30**：附录出一张「逐条编码明细」表（每条一行）：

```
| # | 原话（节选/脱敏） | 模块/活动类型 | 问题类型 | 情感 | 严重度 | [京东C端场景：level1-2 / 优先级] |
|---|---|---|---|---|---|---|
| 1 | [节选] | [模块] | [问题类型] | [正/负/中] | [阻断/影响体验/轻微] | [产品·B2C / A] |
```

- **N ≥ 30**：**不进文档**，导出到工作目录 `coding-detail.csv`（列同上）。文档此节只留一句指引：

```
逐条明细见 `coding-detail.csv`，共 N = … 条。规模较大，外置便于过滤/排序/二次加工。
（做了范围过滤时：csv 保留全量并加「是否相关 + 剔除原因」列，便于复核边界。）
```

> 节选规则：原话过长（>40 字）截前 30 字加「…」；脱敏删除姓名/电话/订单号/尾号等 PII，不损失痛点含义。

## 附录 C、《本次运行说明》（固定附在最后，五部分齐全）

> 让使用者知道这份分析建立在什么之上、哪里可能不牢。逐项填实，没有的写「无」。


## 形态示意（仅示范「长什么样」，**勿照抄内容**——务必按真实反馈重写）

> 下例是凭空编的格式演示，不是任何正典内容、不是真实数据，也不针对真实项目。看完格式即弃。

```
## 关键问题摘要
**一句话主线**：用户被自动加入活动 → 想退找不到入口/退不掉 → 影响价格 → 客服未解。
**最关键变量 = 问题性质·"退出"**：退出一类占全部不满 59%，不满率 36%（大盘 22%）。

| # | 抱怨什么 | 规模 | 不满率 | 主责 | 机会点 |
|---|---|---|---|---|---|
| 1 | 想退退不掉、找不到退出入口 | 323（占不满45%） | 38% | 产品·设计·运营 | 已报管理一键/批量退出+状态可视 |

### 痛点 1 ｜ 想退却退不掉
**规模**：323（占不满 45%），不满率 38%。｜严重度 阻断
- 代表原话：「我勾选了退出，但上面是0，删除不了」「我每天都要退1次」
- 产品：退出与报名不对称，缺自主/批量退出
- 设计：退出入口可发现性差、退出后无状态反馈
- 运营：被动报名+"当天不可退"规则是投诉源，需重审告知
- 机会点：已报管理做一键/批量退出+实时状态；"暂不可退"显性告知原因（待原型验证）
⚠️ 本例格式演示。趋势因有版本元数据才敢标方向；原话已脱敏且真实；机会点为未验证建议。
```

> 注意上例如何：**结论/问题在最前**、每条痛点拆了产品/设计/运营且带机会点、代表原话已脱敏、就地标注了 draft 与"未验证建议"——**形式照此，内容必须按真实反馈重新生成**。
