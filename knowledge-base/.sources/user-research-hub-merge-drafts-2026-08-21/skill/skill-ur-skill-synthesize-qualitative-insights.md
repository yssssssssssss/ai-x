## 一、主题归纳骨架（聚类的产出）

固定结构：**多层分类（level2 主题 → level1 类目 → 便签）**，每个主题挂频次与代表证据，标 D/Q。

```
# 主题归纳（研究目标：[一句话复述本次目标]）

## 主题 1（level 2）：[第一人称的高层主题，如「我希望省心地完成 X，而不必逐步操心」]
  出现：[N 份材料 / M 位用户]    主导情感：[正/负/中，若适用]

  ▸ level 1 类目 1.1：[详细短语/句子，第一人称描述用户行为与意愿]
      频次：[出现在哪几份材料/用户，如 用户A、用户C、用户F]
      代表原话（已匿名）：
        - "[原话 1]" —— [代称，如 用户A]
        - "[原话 2]" —— [代称]
      标记：[D: 用户提到的设计想法 / Q: 待后续研究的疑问 / 无]

  ▸ level 1 类目 1.2：[…]
      …

## 主题 2（level 2）：[…]
  …

> 标注：[凡某主题的方法依据来自 draft 正典、或某类材料用了通用兜底，在此就地标一句]
```

写法约束：
- **频次必须真实可回溯**：每条频次都能在用户给的材料里点到名（哪份/哪位），绝不为凑高而虚标。
- **level 1 标签用第一人称完整短语/句子**描述用户行为与意愿，不要退化成干巴巴的名词（"签到" → "我担心错过连续签到的奖励"）。
- **D / Q 标记**沿用亲和图正典：`D` = 用户提到的产品设计想法，`Q` = 需后续研究的问题，其余为痛点/体验。
- **层级按材料量伸缩**：材料少、主题不多时可以只有 level 1；材料多时才升 level 2。不必硬凑两层。
- **保留反面例证**：若有与主流主题相悖的个案，单列一条"反面/特殊情况"，别丢掉。

### 可选：数字化亲和图骨架（一张表替代"便签墙"）

材料较多、或对方想要"一面看全"的视图时，可附此表（否则省略）：

```
| 便签（一条发现，完整句） | 来源（材料/代称） | D/Q | level 1 类目 | level 2 主题 |
|---|---|---|---|---|
| [一句话发现] | [用户A] | [D/Q/—] | [类目标签] | [主题标签] |
| …                       |        |      |             |             |
```

## 二、结构化洞察骨架（拔高的产出）

每条洞察都走完"结果→结论→洞察"，并按洞察定义结构化、配论据。

```
## 洞察 N：[一句话洞察陈述——可指导行动的策略判断，不是现象复述]

  - 用户：[谁]
  - 场景：[在什么具体场景下]
  - 任务：[想完成什么]
  - 情感需求 / 价值：[希望达成的深层价值]
  - 矛盾 / 障碍：[但面临的具体矛盾或障碍]

  推导链（自检：别停在结果或结论）：
  - 结果（观察到的）：[来自主题归纳的事实/频次，如「N 位用户提到 X」]
  - 结论（高度凝练的原因判断）：[凝练，不是复述现象]
  - 洞察（可行动的策略建议）："如何呢、又能怎" → [策略建议]

  所用框架：[用户旅程地图 / 价值主张画布 / 同理心地图 / ABC —— 写明为何选它]
  论据（论点配论据）：
    - 主题来源：[挂到第一部分的哪个主题，频次多少]
    - 代表原话（已匿名）："[原话]" —— [代称]
  延伸：[D: 由此可探索的设计机会 / Q: 仍需验证的问题 / 无]

  > 标注：[若本条所用框架/方法来自 draft 正典，或证据偏单薄，在此就地标一句]
```

要点：
- **一条洞察选一个最贴的框架**承载，不要四个框架全套上。选型按正典（流程情绪→旅程图；共情/典型用户→同理心地图；检验方案→价值主张；单一矛盾→ABC）。
- **论点必配论据**：每条洞察都要能挂回主题与原话；挂不上的，要么降级为"待验证假设"、要么删掉。
- **洞察 ≠ 痛点清单**：如果写出来还是"用户觉得 X 不好用"，说明只到结果层，继续往上拔。

### 可选：分层 / 阶梯洞察变体

当几条洞察是"逐层进阶 / 成熟度阶梯 / 需求金字塔"这类**层级关系**时用此形态（否则用上面的平铺洞察）。透镜按层级含义选一个（见 SKILL.md 第 2 步分层 models 行）：

```
## 分层洞察：[一句话点出这是一条怎样的进阶主线，如「从『省力完成』到『被懂得』的三层价值进阶」]

  所用透镜：[means-end 价值阶梯 / user-needs 需求深浅 / kano 需求强度·发展阶段 / user-cultivation 养成阶段 —— 写明为何选它]

  - 第 1 层：[层名] —— [这一层的定义 / 用户在此层要的是什么]（证据：[主题 / 频次 / 匿名原话]）
  - 第 2 层：[层名] —— [定义]（证据：…）
  - 第 3 层：[层名] —— [定义]（证据：…）

  用户当前所处层：[多数用户停在第几层 + 依据]
  目标层：[想把用户带到第几层 + 为什么]
  > 天然适合配示意图（阶梯 / 金字塔，见 delivery-skeleton.md 示意图形态库）。
```

### 负向边界（标准动作，别省）

正向洞察之外，显式给一段"需求不在哪 / 不该硬推哪"：

```
## 负向边界：不该做 / 不该硬推的

  - [某方向 / 功能]：[为何不该] —— 依据：kano [无差异型：做了也没用 / 反向型：做了反招不满] 或 user-needs [这是某类用户的个性需求，不能推广为普适]（证据：[原话 / 频次]）
  - …
```

## 四、形态示意（仅示范"长什么样"，**勿照抄内容**——务必按真实材料重写）

> 下例是凭空编的格式演示，不是任何正典内容，也不针对真实项目。看完格式即弃。

```
## 主题 2（level 2）：我想"顺手"表达心意，而不是为送礼专门安排一场任务

  出现：4 份材料 / 5 位用户    主导情感：偏正向（被"仪式感"困住时转负）

  ▸ level 1 类目 2.1：我会在生日/纪念日这种私人节点临时起意想送点东西
      频次：用户A、用户C、用户D、用户F
      代表原话（已匿名）：
        - "其实不一定非得过节，想到了就想给她寄点小东西" —— 用户A
        - "上次纪念日前一天才想起来，现找特别慌" —— 用户D
      标记：Q（"临时起意"的比例与触发点需定量验证）

  ▸ level 1 类目 2.2：但流程让我觉得"送礼"像一件要正经筹备的任务
      频次：用户C、用户F
      代表原话（已匿名）："挑、包装、写卡片……一套下来挺有压力的" —— 用户F
      标记：D（用户提到"希望有个一键搞定的轻量入口"）

---

## 洞察 1：把"送礼"从节庆任务，重做成可顺手完成的日常表达

  - 用户：有送礼习惯的年轻用户
  - 场景：生日/纪念日等私人节点临时起意时
  - 任务：快速送出一份能表达心意的小礼
  - 情感需求/价值：用低负担的方式维系亲密关系、不被"仪式感"绑架
  - 矛盾/障碍：现有流程把轻量心意变成了要专门筹备的任务

  推导链：
  - 结果：5 位用户中 4 位描述"临时起意"，2 位明确抱怨筹备压力
  - 结论：用户的真实需求是"低负担的即时表达"，而非"更隆重的送礼"
  - 洞察（如何呢、又能怎）：弱化"节日筹备"心智，做"顺手表心意"的轻量即时入口，
    联动即时零售缩短从起意到送达的链路

  所用框架：价值主张画布（检验"轻量即时入口"是否击中"低负担表达"这一收益）
  论据：
    - 主题来源：主题 2（4 份材料/5 位用户）
    - 代表原话："想到了就想给她寄点小东西" —— 用户A
  延伸：D（轻量送礼入口）；Q（"临时起意"占比待定量）

  > 标注：所用框架依据当前为 draft 的 qualitative-insight-frameworks，结论待团队与定量验证。
```
