# 设计策略 / 05 评审验证


## 目标

让设计策略可以被评审、被决策、被上线后验证。

## 汇报结构

| 部分 | 说明 |
| --- | --- |
| 背景 | 项目为什么重要，覆盖哪些用户和业务场景 |
| 问题 | 用用户、竞品、业务、数据证据说明现状问题 |
| 归因 | 收敛 2 到 4 个高阶问题 |
| 策略 | 说明每个问题对应的策略层 |
| 动作 | 展示触点级设计措施 |
| 价值 | 对应用户收益、业务收益和验证指标 |
| 决策 | 说明需要评审确认的规则、优先级、取舍和风险 |

## 验证模板

| 策略目标 | 过程指标 | 结果指标 | 观察周期 | 风险预案 |
| --- | --- | --- | --- | --- |
| 降低认知混乱 | 关键说明点击率、规则展开率 | 咨询量、误解反馈 |  |  |
| 降低感知复杂 | 关键触点点击率、停留时长 | 转化率、流失率 |  |  |
| 打通路径阻断 | 任务完成率、回访率 | 加购率、预约成功率 |  |  |
| 降低维护成本 | 配置项数量、异常场景数量 | 运营修改次数、复用率 |  |  |

## 输出物

- 评审叙事
- 决策问题清单
- 上线验证计划

## 适用条件

- 输入包含已确认问题、约束与策略目标，且研究问题与本方法的目标一致。
- 若缺少必需材料，先记录缺口，不以知识库内容替代当前事实。

## 输入

- 已确认的研究目标、范围、约束和成功标准。
- 与本方法相关的可追溯用户输入、公开来源、截图、数据或既有证据。

## 执行步骤

1. 冻结研究问题、分析对象和证据边界。
2. 按本卡片正文中的维度或模型整理输入，并逐项保留来源引用。
3. 区分观察事实、分析推断和待验证假设。
4. 形成结构化输出，检查覆盖、冲突、缺口和不可照搬边界。

## 输出

- 与正文模板一致的结构化分析结果。
- 来源引用、证据缺口、风险和后续验证项。

## 常见误用

- 把方法或案例当作当前业务事实。
- 为填满模板而编造数据、用户结论或竞品能力。
- 忽略样本、时间、场景和证据适用范围。

## 证据边界

知识库只提供方法依据。当前用户、竞品和业务事实必须来自本次用户输入或可复查证据；无法核验的内容只能标为假设或缺口。

## 验证方式

- 检查每项事实是否有来源，每项推断是否引用事实，每项建议是否给出指标或验证方法。
- 使用第二来源、反例或人工复核验证关键结论；不能验证时明确降级。
