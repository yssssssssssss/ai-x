# 转化漏斗分析 · 输出骨架与模板

> 本文件是 **conversion-funnel-analysis skill 自己的产出结构**，不是 wiki 正典。
> 分步转化率/流失率算法、总转化率连乘、宏微转化定义、Fogg 行为模型 B=MAP 五类根因、Baymard 放弃原因、漏斗口径定义清单与诊断假设清单的口径等正典内容**一律运行时从 `research-wiki/` 现读**（见 SKILL.md 第 2 步），不在此复制。
> 下面方括号 `[…]` 是占位槽，按本次 brief、读到的正典、以及用户提供的真实分步数据填实。**严禁脑补数据**：分步人数/转化率/分群差异都要有素材出处；**Fogg 根因一律以「假设/待验证」落笔**，不写成已证实的原因。

## 一、直接诊断模式 · 输出骨架（有分步数据时，默认）

开头先用一句话交代：**诊断对象（哪条路径）/ 宏转化目标 / 诊断场景（监控预警·病灶未知·改版回测·新功能采纳）/ 数据形态（分步人数·分群明细·改版前后对比）/ 口径要点**。

> **写法总则（可读性命门，逐节适用）**：发现层只写「结论 + 证据」，不写推导过程。① 不复述方法（「为什么看相对流失」「转化率公式」不必讲一遍）；② 不留竖式草稿（算式收进括号/脚注，正文只给结果，如「基线 ≈ 65.6%（反算）」）；③ 不写元评论（「典型病灶信号」「三个信号一致指向」「看相对流失不被绝对骗」这类对自己分析的旁白，删）；④ 依据/边界（draft、假设待证、未覆盖、数据待校验）归口到「口径小结 / 数据可信度 /《本次运行说明》」，发现层最多留一句轻量 ⚠️。判据：删掉某句后结论与证据还在，那句就是赘述、删。

### 0. 诊断结论摘要（结论先行，放最前）

```
- 一句话核心判断：[这条路径卡在第几步「X→Y」+ 该步相对流失多大、明显高于前后步/基线 + 最可能是哪类根因（假设）]
- Top 优化建议速览（每条：流失环节 → 疑似根因[Fogg 五类之一] → 一句怎么优化 → 怎么求证/回测）：
  1. [环节] → [疑似根因] → [优化动作] → [录屏/可用性测试/深访/VOC / A/B 回测]
  2. …
```

### 1. 口径小结（先约定再算）

```
- 宏转化目标：[例：完成开通并首次使用某功能]
- 步骤序列（3–7 步、互斥必经、中性名）：[步1 → 步2 → 步3 → …]
- 漏斗类型：[开放 / 封闭]     时间窗：[整体或步间时限]
- 计数口径：[每用户一次 / 每会话一次]     顺序要求：[直接跟随 / 间接跟随]
- 可用分群维度：[渠道 / 设备 / 新老 / 版本 …]
  > 标注：[口径里哪些是用户给的、哪些是合理假设——假设的在此标一句；口径不同结论可能相反]
```

### 2. 数据可信度校验

```
- 埋点/数据质量：[每步是否有对应事件、参数是否完整、有无漏报/重复触发、步骤是否互斥必经]
- 结论：[可信 / 部分待校验 → 标「数据待校验」的步骤与影响]
```

### 3. 分步转化率 / 流失率 + 总转化率（核心量）

```
| 步骤 | 进入人数 U_n | 分步转化率 U_{n+1}/U_n | 分步流失率 | 备注 |
|---|---|---|---|---|
| 步1 [名] | [数] | [%] | [%] | |
| 步2 [名] | [数] | [%] | [%] | |
| … | | | | |
| 宏转化终点 | [数] | — | — | |

- 总转化率（各步连乘）：[%]
- （长链路可补微转化中间步，避免只看首尾错失中段）
```
> 表即结论：直接给算好的数字，**不必在正文另印 `转化率=U_{n+1}/U_n` 公式或列竖式推导**。

### 4. 最大流失环节定位（看相对流失，不看绝对人数）

```
- 最大流失环节 = 第 [n] 步「[X→Y]」，相对流失 [%]。依据（一行）：高于前后步（[a%]/[b%]）｜高于基线/经验值（[c%]）｜命中[改动范围/某分群]。
- （若绝对流失最多的是另一步）一句带过：第 [X] 步绝对流失最多（[N] 人），但属[未改动的天然分流/入口跳出]，非病灶。
- 宏/微转化：一句话——[病灶是否贴近宏转化终点、中段是否健康]。
```
> 直接给结论 + 证据，**别写整段「为什么是它、而不是第 1 步」的排除式推导**（那是思考过程，不是结论）。

### 5. 分群下钻（拆穿「平均的谎言」）

```
分群对比矩阵（步骤 × 分群维度值，填分步转化率，标出明显低于行均值的格子）：
| 步骤 | 整体 | [渠道A] | [渠道B] | [新用户] | [老用户] | [v旧] | [v新] |
|---|---|---|---|---|---|---|---|
| 步2→步3 | [%] | [%]⚠️ | [%] | … | | | |

- 收敛结论：[是「普遍问题」还是「特定人群/渠道/版本问题」→ 异常人群 × 异常环节的交叉点]
- （改版回测场景）：[改动前后同口径分步转化率对比，量化收益或退化]
> 无分群数据时：明确声明「未分群，整体平稳可能掩盖某渠道/设备/版本的结构性退化」，并索要分群数据。
```

### 6. 归因假设（Fogg 五类，一律「假设/待验证」）

```
对最大流失环节，按 Fogg B=MAP 五类列疑似根因（口径取自 conversion-funnel.md，运行时现读）：
| 疑似根因（五类之一） | 观测信号 | 假设内容 |
|---|---|---|
| [认知不足/动机不够/操作能力门槛/信任顾虑/技术故障] | [如该步长停留后退出、表单报错率高、特定设备集中流失…] | 假设：[…] |

> 每条都是**假设**，不是结论；须接第 7 步定性求证才能定论。
```

### 7. 定性求证方向

```
| 待证假设 | 求证方法 | 衔接 |
|---|---|---|
| [假设1] | [录屏 / 可用性测试 / 深访 / VOC / 表单字段分析 / 错误监控] | [interviews.md / voc-analysis.md …] |
```

### 8. 优化建议 + 回测方案

```
- [针对假设根因的可落地优化：降门槛 / 补提示 / 减顾虑 / 修故障 …]
- 回测方案：[同口径漏斗对比改动前后分步转化率 / A/B 实验严格验证因果]
- （多个待改环节需排序时）：叠加 issue-prioritization 排 P0/P1/P2
```

### 9. 诊断范围与未覆盖（诚实声明边界）

```
- 本次数据覆盖：[诊断到了哪条路径/哪些步骤/哪些分群]
- 未能覆盖：[数据没覆盖的步骤/人群/时间段 → 标「未覆盖」，不假装诊断过]
- 靠假设的根因：[哪些根因证据偏薄、属 Fogg 假设，需定性求证]
- 数据待校验：[埋点存疑、影响结论的地方]
```

## 二、框架模式 · 输出骨架（无数据时）

> 末尾必须**明确索要分步数据**：拿到后即可切到「直接诊断」。

### 1. 口径清单（按正典「漏斗定义清单」逐项）

```
请先与我确认（口径不同，算出的转化率会不同、跨期没法比）：
- 宏转化目标？ 步骤序列（建议 3–7 步、互斥必经、中性名）？
- 开放 / 封闭漏斗？ 转化时间窗？ 每用户 / 每会话计一次？ 直接 / 间接跟随？
- 能拆哪些分群维度（渠道/设备/新老/版本）？
```

### 2. 步骤拆解建议（针对用户这条具体路径）

```
一版拆步骤草案（供确认，可含微转化中间步）：
[步1 → 步2 → 步3 → … → 宏转化终点]
> 用中性步骤名而非具体字段名；发散路径先做路径分析再决定是否建漏斗。
```

### 3. 埋点校验清单

```
开工前逐项确认：每步有对应事件 / 参数完整 / 无重复触发 / 无漏报 / 步骤互斥必经。
```

### 4. 分群维度建议

```
建议拆：渠道来源 / 设备 / 新老用户 / 版本号 —— 以便定位「异常人群 × 异常环节」，别被平均值骗。
```

### 5. Fogg 五类诊断假设清单（口径取自正典，运行时现读）

```
| 流失原因类别（五类） | 观测信号 | 求证方法 |
|---|---|---|
| 认知不足（缺提示） | [如长停留后退出、反复返回上一步] | 录屏、可用性测试 |
| 动机不够 | [进入即跳出、跳过非必填] | 深访、VOC |
| 操作能力门槛 | [表单报错率高、需切换设备] | 录屏、表单字段分析 |
| 信任顾虑 | [涉隐私/资质处停滞] | 深访、问卷 |
| 技术故障 | [错误日志、特定设备/版本集中流失] | 错误监控、分群漏斗 |
> 别默写——运行时从 conversion-funnel.md 的「诊断假设清单」现读，此表仅示意结构。
```

### 6. 出图建议

```
漏斗图（分步进入人数+转化/流失率）/ 分群对比矩阵（步骤×分群）/ 到达耗时拆解。
```

### 7. 给用户的数据索要

```
要直接帮你诊断，请发我：① 这条路径每一步的进入人数（3–7 步）② 可拆的分群明细（渠道/设备/新老/版本）③ 若是改版评估，改动前后的同口径数据 ④ 相关的用户反馈/客服记录（辅助归因）。
```

## 五、形态示意（仅示范「长什么样」，**勿照抄内容**——务必按真实路径与数据重写）

> 下例是凭空编的格式演示，不是任何正典内容、不是真实数据结论，也不针对真实项目。看完格式即弃。

```
本次诊断：某「开通并首次使用」路径（封闭漏斗，7 天窗，每用户计一次），场景=病灶未知快速收敛。数据=分步人数 + 分渠道/分版本。

【结论摘要】路径卡在第 3 步「填写资料→提交」，分步流失率 42%，明显高于前后步（<15%）与上版基线（28%）；结合「表单报错率高、v8.2 集中流失」，最可能是**操作能力门槛/技术故障**（假设）。
Top 优化：① 第3步提交 → 疑似技术故障（v8.2 报错） → 先修 v8.2 提交报错 → 错误监控 + 分版本漏斗回测 ② …

【口径】宏转化=完成开通并首用；7 步；封闭；7 天窗；每用户一次。（步骤名为假设，待与埋点确认）

【分步转化率】步1→2：88%｜步2→3：85%｜步3→4：58%⚠️｜…｜总转化率：31%

【最大流失环节】第 3 步「填写资料→提交」，相对流失 42%（高于前后步 <15%、上版基线 28%）。首步绝对流失最多但属天然分流，非病灶。

【分群下钻】步3→4：整体58%，但 v8.2=41%⚠️、v8.1=72%；→ 特定版本问题，收敛到 v8.2 × 第3步。

【Fogg 根因假设】操作能力门槛（假设：字段多/报错）；技术故障（假设：v8.2 提交接口报错）——均待求证。

【定性求证】调 v8.2 该步录屏 + 看错误日志；跑一轮可用性测试看表单卡点。

【未覆盖】无分设备数据，未判断是否某机型专属；【数据待校验】步3事件疑似重复触发，需核。
⚠️ 本诊断基于 draft 正典（conversion-funnel 当前 draft），根因均为 Fogg 假设，需定性求证后再定论。
```

> 注意上例如何**先定口径再算**、如何**用相对流失而非绝对人数定位**、如何**分群下钻收敛到「版本×环节」**、如何**把根因写成「假设」而非结论**、如何**每条都是「结论+证据」而不叙述推理过程/不复述方法/不写元评论**、如何**只基于给定数字不脑补**、如何**诚实标「未覆盖 / 数据待校验」**——形式照此，内容必须按真实路径与数据重新生成。
