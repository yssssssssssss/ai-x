# gold:run 对金标场景自动确认 HITL 闸门

## 背景与决策

`spike:plan` 与 `spike:execute` 之间有一道 HITL 硬闸门:plan 生成待确认计划后物理停下,人工确认才能 execute。这道门是防止未经审视的计划擅自调用真实能力(烧 token、打真实网络、触发审批)的核心保护。

金标真实运行需要在一次命令内连跑 plan→execute 三遍,这与"人工逐次确认"直接冲突。我们决定:`gold:run` **对预先定死的金标场景自动确认计划**,但保留闸门语义——脚本在 execute 前**断言计划不含 `requires_approval` 步骤**,一旦命中审批步立即停止,绝不自动放行。

## 权衡

金标场景的计划结构预先确定且已知安全(仅公开信息、无 PII、无需审批,见规划 fixture 的 `D6_data_sensitivity=satisfied`),因此对它自动确认不引入新风险。若不自动确认,批次机制就退化成"手敲三遍 + 手工拷产物",既违背可复现,也让长期审计包的裁剪清单靠自觉必漏。

自动确认**只对这个已知安全的金标场景放行**,不是移除闸门——`requires_approval` 断言是最后防线,任何需审批的计划仍会中断。这是"KISS 地复用现有 plan/execute + 一道断言",而非新建审批系统。
