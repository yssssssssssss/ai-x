# 金标验证坚持全真闭环,不接受半真取样

## 背景与决策

"真实能力闭环"可以有三档真实度:全真(真 LLM 网关 + 真 Tool)、半真(真 Tool + mock LLM,或仅关键步真)、mock。我们决定金标验证**只接受全真**:`gold:run` 强制 `LLM_PROVIDER=gateway` + `TOOL_ADAPTER=real`,规划、执行、报告生成全程真实 LLM,检索走真实网络;不依赖 `.env` 的当前值(`.env` 保留 `fake` 供日常离线测试)。

## 权衡

研究员评审的对象是**真实生成的报告文本**——结论有没有观察事实支撑、数据缺口有没有被隐藏、URL 是否被伪造。这些只有真 LLM 读真检索结果生成时才谈得上。半真(mock LLM)让评审对象是预置 fixture 文案,评审沦为走过场,正是 CONTEXT.md `_Avoid_` 的"演示闭环";也让 P0 硬失败的"来源伪造"无从检出。

代价:全真运行实际消耗 gateway token + Tavily 配额、打真实内网,慢且受网关波动影响。用"金标场景只一个、批次只三次、infra 失败可重试不占名额"控制成本,而非降低真实度。`gold:run` 不读 `.env` 的 provider/adapter 值而强制设定,确保任何环境下发起的金标运行都是全真,杜绝误用 mock 产出冒充金标样本。
