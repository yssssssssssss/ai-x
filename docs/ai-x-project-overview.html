01项目概览

ai-x 不是“把问题发送给大模型，再返回一段文本”的聊天应用，而是一套面向用户研究工作的 AI 任务编排与可信交付平台。它把需求变成版本化合同，把能力变成确认前可见的执行 DAG，把执行结果变成带 Evidence、Review 和 lineage 的正式研究产物。

核心判断：技术运行成功 ≠ 研究结果可用。系统最终追求的是“真实能力闭环”——真实输入、真实 LLM、真实 Tool、可追溯报告，以及独立研究员对结果可用性的判断。
Input

需求可确认

显式区分研究规划与直接回答，记录范围、假设、歧义、成功标准、敏感性与 PII。

Execution

过程可审计

计划、Skill、Tool、Knowledge、LLM、审批、Evidence 和 Artifact 都绑定 Task／Plan／Attempt。

Delivery

结果可追溯

Reviewed Canonical 是唯一事实源；完整报告负责审计，编辑摘要负责决策阅读。

业务定位

  • 规划用户研究：目标、方法、样本、排期、采集模板和验收标准；
  • 基于现有 Evidence 直接回答业务问题，形成策略与优先行动；
  • 支持竞品、行业市场、VOC、设计走查和无障碍审计；
  • 组合方法知识、公开检索、数据集、截图和专业分析工具；
  • 为研究员与决策者分别提供完整底稿和编辑摘要。

02核心能力

Requirement

需求理解与多轮澄清

自然语言输入先进入 ResearchTaskV2；不能安全推断的关键内容进入 awaiting_clarification，回答后形成新的 Requirement Version。

Planning

问题图与方案比较

生成 ProblemGraph、Evidence Policy、Capability Demand，并提供 2～4 个候选方案；至少包含 speed／depth，只有推荐、没有自动替用户选择。

Modes

任务级双编排

single_skill 使用 Plan v2 且恰好一个 Invocation；multi_skill 使用 Plan v3、Portfolio、Contribution、唯一 Synthesizer 与 Ledger。

DAG

可见且冻结的执行图

Compiled Skill 在确认前展开 Knowledge／Tool／LLM／Skill／Reviewer 阶段；执行时不得临时加入隐藏步骤或嵌套 Agent。

Evidence

证据约束

公开来源、截图、用户输入、Knowledge、数据集、模拟和派生结果分级；Required Evidence 与 Core Tool Evidence 不满足时失败关闭。

Report

Canonical + 双报告集

Reviewed Canonical 是唯一事实源；Canonical Detail 保留完整内容，Editorial Summary 提供安全、无脚本的决策摘要。

Multimodal

多模态与数据输入

计划级图片、截图、数据集 Gate；支持安全图像校验、标注、Chart SVG、Manifest、lineage 与导出策略。

Control

长任务治理

JWT、owner 隔离、状态版本、命令幂等、Lease、Heartbeat、Retry、Replan、Cancel、Checkpoint 与 completed_with_gaps。

03技术特点

Contract-first

TypeScript、JSON Schema、YAML Registry 和数据库约束共同定义边界。Prompt 负责语义，不负责偷偷改变协议。

Plan before Execute

成本、风险、输入与审批在真实调用前显式化；用户确认的是最终冻结 DAG。

Fail-closed Content

Evidence、来源身份、Coverage、Review 或 Artifact 完整性错误阻断交付；布局与可选视觉能力才允许降级。

Immutable Provenance

SEALED Artifact 绑定 Schema、SHA-256、字节大小、敏感级别、Task／Plan／Attempt 和父子 lineage。

Model / System 分权

模型处理语义；系统处理 ID、引用、Hash、状态、Coverage、授权和发布；Renderer 不重新研究。

Recoverable Parallelism

DAG 按依赖分 wave 并发执行；Lease 心跳、fencing、检查点复用和精确失败动作支撑长任务恢复。

关键不变量

  1. 用户选择编排模式和执行方案；推荐不等于自动选择。
  2. 模式随 Task 冻结，单／多 Skill 不跨模式 fallback。
  3. 所有真实 LLM 与 Tool 调用都必须留下可验证回执。
  4. supported 事实必须绑定有效 Evidence；虚拟用户只产生 simulation 假设。
  5. Final Review 之后的 Reviewed Canonical 是唯一正式事实源。
  6. Summary 可以概括，不能新增事实；Summary 失败不阻断 Detail。

PostgreSQL 保存任务控制事实；大体积 JSON、图片、SVG、HTML 和报告包位于 Artifact Workspace。配置与能力定义保留在 Git，不写入业务数据库。

05核心流程

输入与模式提交研究目标，并选择 single_skill 或 multi_skill。
需求冻结形成 ResearchTaskV2；必要时多轮澄清并版本化。
问题与能力ProblemGraph、Evidence Policy、Demand、Capability Resolution。
候选计划生成 2～4 方案，编译并保存 Plan v2／v3 与 hash。
选择与 Gate用户选择、确认输入、上传图片／数据集并完成审批。
Lease 执行按 DAG wave 运行 Knowledge、Tool、LLM、Skill、Reviewer。
证据与审校封存 Evidence Manifest、Canonical，执行 Final Review。
报告与发布Detail、Summary、Markdown／ZIP／HTML，以及可选 Zero。

任务状态机

awaiting_clarification→ awaiting_selection→ awaiting_confirmation→ awaiting_approval / ready→ executing→ reviewing→ composing_report→ completed(_with_gaps)

执行过程还可以进入 paused、failed、cancelled 或 rejected。所有状态变更使用 stateVersion 做乐观并发控制。

Single Skill · Plan v2

Requirement → Capability Resolver → 1 Skill Invocation → compiled stages / legacy call → Evidence → Canonical → Review → Reports

关键保证是 Task 中恰好一个 Skill Invocation；失败时不得自动切换到多 Skill。

Multi Skill · Plan v3

Requirement → Demand Graph → Portfolio → Contributors → Bundle → Synthesizer → Cross Review → Ledger → Canonical → Reports

每个 Question + Contribution Type 有唯一主责；Ledger 记录 included、merged、conflicted 或 omitted。

Truth

Canonical Detail

正式研究交付和追溯入口，保留 Direct Answer、Finding、请求交付物、Evidence、行动、限制、风险和多 Skill 审计。

Reading

Editorial Summary

从冻结 Source Bundle 派生，可合并重复信息，但不能新增事实、数字、日期、URL 或提高证据确定性；失败不影响 Detail。

完整性门禁

  • 每个必答问题都有 Direct Answer，或明确标记为未回答；
  • supported 事实绑定已验证 Evidence；Recommendation 可回溯至 Finding／Summary；
  • 请求交付物形成结构化内容，而不是只出现在清单中；
  • ReportDocument 覆盖 Canonical 中要求展示的内容叶子；
  • Chart、图片、标注验证 Asset、Manifest、Spec、Evidence 和 lineage；
  • 生产 Summary 禁止 JavaScript、事件属性和运行时网络请求。

08治理、失败与恢复

场景系统行为
Requirement 不完整停在澄清，不生成正式计划，不调用真实 Tool。
审批或输入未完成停在确认／审批，不获取执行 Lease。
Optional Tool／Contributor 不可用按合同形成 Gap；可继续并最终成为 completed_with_gaps。
Core Tool／Required Evidence 不足失败关闭，不生成正式报告。
Skill／Knowledge／Contract hash 漂移要求 Replan，不静默使用新版本。
可重试外部故障进入 paused，保留失败类型与允许动作。
Final Review 不通过暂停；只允许受控目标化修订，不允许任意全文重写。
Layout／可选展示失败确定性降级，不改变 Canonical 内容。
Lease 丢失／发布未完成停止写入、失效未完成 Artifact，由恢复逻辑处理。
Identity

身份与并发

Bearer JWT、用户状态检查、Task／Conversation owner 校验、State Version 和 Command Idempotency。

Trace

调用回执

记录 provider、endpoint、requested／actual model、prompt hash、context hash、trace、token 与失败；model drift 失败关闭。

Artifact

文件安全

安全根路径、文件身份、大小和 hash 复验；限制图像字节与像素，拒绝 SVG 脚本、事件和外部资源。

Gold

真实能力验收

金标路径要求三次全真运行、真实 Gateway 与 Tool、独立研究员评审；来源伪造、泄密和绕过确认属于硬失败。

09当前成熟度与边界

已经形成的基础

  • 需求到交付的 Current 全链路具有明确模块和合同；
  • 单／多 Skill、Plan v2／v3、Evidence、Review、Canonical 和 ReportPackage 均有实现；
  • 控制平面覆盖状态、幂等、Lease、Artifact、模型回执和恢复；
  • 62 份 JSON Schema、15 个迁移、11 份 ADR、216 个测试文件；
  • 行业市场分析已进入 active Deliverable 与 compiled Skill；
  • Web 统一新任务与 Current 历史任务恢复主链。

必须正确理解的边界

  • 示例配置中 Multi Skill、Report v3、Editorial Experience、Showcase、Standalone HTML 与 Zero 默认关闭。
  • 真实闭环依赖 Gateway、Tavily、PostgreSQL 和相应凭证；fake Tool 不构成真实证据。
  • 25 个 active Skill 中 19 个仍是 Legacy，阶段级审计与恢复粒度较弱。
  • Optional Lab 与内部 API 不保证常在，缺失时必须诚实形成 Gap。
  • 多代 Plan／ReportDocument／ReportPackage Reader 并存，提高维护复杂度。
  • 自动 Review 不能替代独立研究员的业务可用性判断。

10结论

ai-x 的本质是一套以 Evidence 和可审计执行为核心的用户研究生产系统。它的价值不只在于生成报告，而在于把研究工作转化为可确认的需求、可比较的方案、可冻结的执行合同、可追溯的证据和可审校的正式交付。

项目最突出的能力是单／多 Skill 双合同、完整 provenance、内容失败与布局降级分离、Canonical 双报告集，以及由 State Version、Idempotency、Lease、Hash 和 Schema 支撑的长任务恢复。

当前最需要持续关注的不是增加更多抽象，而是让现有能力在真实环境稳定闭环：提高 active Skill 的 compiled 比例，明确部署开关，保持 Core Evidence 通道可用，并持续用真实任务与独立研究员评审验证研究可用性。

综合判断：项目已经超出原型式“LLM + Prompt + 页面”，进入“研究任务控制平面、专业能力编排与可信报告基础设施”阶段。其成熟度应由真实证据链和研究员可用性衡量，而不能只看接口成功、测试通过或页面完整。
